## Алхам 3: Ачааллыг шатлан өсгөх — 5 / 30 / 100 VU

Заавар ёсоор `stages` биш, `script.js`-ийг тусад нь ажиллуулж, түвшин бүрийн summary-г тусад нь авсан.

```bash
k6 run --vus 5   --duration 1m script.js | tee results/run-05vu.txt
k6 run --vus 30  --duration 1m script.js | tee results/run-30vu.txt
k6 run --vus 100 --duration 1m script.js | tee results/run-100vu.txt
```

| VU | p90 | p95 | med | max | throughput | алдааны хувь |
|---|---|---|---|---|---|---|
| 5 | 224.27 ms | 226.94 ms | 148.88 ms | 229.36 ms | 7.56 req/s | 0.00% |
| 30 | 226.36 ms | 226.73 ms | 153.33 ms | 231.78 ms | 46.05 req/s | 0.00% |
| 100 | 226.27 ms | 226.86 ms | 215.91 ms | 435.99 ms | 152.94 req/s | 0.00% |

**Нэгж хэрэглэгчийн туршлага муудаж эхэлсэн цэг:** p95 гурван түвшинд бараг өөрчлөгдөөгүй (227 ms орчим тогтвортой байсан) тул сүүлийн (tail) хэмжүүр удаашралтыг тод харуулаагүй. Гэвч **median** утга 5 VU-д 148.88 ms байсан бол 100 VU-д 215.91 ms болж, **max** утга бараг хоёр дахин нэмэгдсэн (229 ms => 436 ms гэсэн үг). Энэ нь p95-ийн сүүл хараахан хөдлөөгүй байхад **typical хүсэлт** аль хэдийн мэдэгдэхүйц удааширсныг харуулж байна. Энэхүү муудал нь 30-аас 100 VU хооронд илт харагдаж эхэлсэн.


VU тоо 1-ээс 100 хүртэл аажмаар өсөж, оргил дээр байсны дараа буцаж 0 болж буурсан. Нэгтгэсэн summary (p95 = 226.9 ms, алдаа 0%) нь дээрх гурван тусдаа ажиллуулалттай нийцэж байгаа бөгөөд заавар ёсоор энэ гаралтыг хүснэгтийн тоо болгон **АШИГЛААГҮЙ**. Зөвхөн ачааллын хэлбэрийг нүдээр баталгаажуулах зорилготой байсан.

## Алхам 4: Thresholds (SLO)

**SLO-гийн үндэслэл:** Алхам 2-ын baseline p95 = 226.94 ms. Threshold-ыг baseline × 1.5 ≈ **340 ms** гэж тогтоосон. Энэ нь хэвийн хэлбэлзэлд зай өгөхийн зэрэгцээ бодит доройтлыг илрүүлэх хангалттай нарийвчлалтай. Алдааны хувийн threshold-ыг лекцийн стандарт **<1%** гэж авсан.

```javascript
thresholds: {
  http_req_duration: ['p(95)<340'],
  http_req_failed: ['rate<0.01'],
},
```

### PASS тохиолдол (`script_slo.js`, `results/run-thresholds-pass.txt`)
30 VU, 1 минут:
```
PASS 'p(95)<340' p(95)=229.78ms
PASS 'rate<0.01' rate=0.00%
```

### FAIL тохиолдол (`script_slo_fail.js`, `results/run-thresholds-fail.txt`)
Ижил ачааллаар, threshold-ыг санаатайгаар `p(95)<50` болгож өгөсгөж, FAIL гаралтыг үзүүлсэн:
```
FAIL 'p(95)<50' p(95)=229.97ms
PASS 'rate<0.01' rate=0.00%
```
Энэ нь `checks` (функциональ зөв эсэх => status 200) ба `thresholds` (SLO/чанарын шалгуур) хоёр бие даасан гэдгийг баталж байна: хариу функционалын хувьд зөв байсан ч latency SLO-г хангаагүй. CI/CD pipeline-д яг ийм механизмаар deploy-г хааж болно.

## Алхам 5: Локал сервер тест (нэмэлт)

Latency-г бусад хүчин зүйлээс (сүлжээний нөхцөл гэх мэт) тусгаарлахын тулд хоёр endpoint-той энгийн Node.js/Express сервер бичсэн:
- `/fast` — шууд хариу өгдөг
- `/slow` — `setTimeout(100ms)` ашиглан санаатай 100ms саатал нэмсэн

Хоёуланг ижил нөхцөлд (30 VU, 30 секунд) тестэлсэн.

| Endpoint | avg | p90 | p95 | throughput | алдааны хувь |
|---|---|---|---|---|---|
| `/fast` | 1.66 ms | 1.89 ms | 5.88 ms | 29.94 req/s | 0.00% |
| `/slow` | 101.43 ms | 102.27 ms | 102.43 ms | 27.22 req/s | 0.00% |

`/slow` endpoint-ийн p95 (102.43 ms) нь кодод оруулсан 100 ms саадтай бараг яг таарч байгаа нь хэмжилт бодит шалтгааныг үнэн зөв тусгаж байгааг баталж байна. Энэ нь Алхам 3-ын `test.k6.io`-гийн үр дүнтэй харьцуулбал ялгаатай — тэнд зэрэгцээ хэрэглэгчийн тоо (5→100 VU) өссөн ч p95 бараг өөрчлөгдөөгүй, өөрөөр хэлбэл тухайн тохиолдолд зэрэгцээ ачаалал бол саатлын гол шалтгаан биш байсан. Харин энд latency-г шууд, санаатайгаар оруулсан бөгөөд үр дүнд шууд, нарийн тусгагдсан нь **latency ба concurrency хоёр тусдаа хувьсагч** бөгөөд тэдгээрийг тусад нь туршиж байж бие даасан үр нөлөөг тодорхой ялгаж болохыг харуулж байна.

## Дүгнэлт

**test.k6.io** дээрх бүх туршилтад p95 latency 5-аас 100 VU хүртэл тогтвортой (227 ms) байсан бол throughput 7.56-аас 152.94 req/s хүртэл шугаман байдлаар өссөн, алдаа 0% байсан. Гэвч **median latency** 100 VU-д мэдэгдэхүйц өссөн нь p95 дангаараа доройтлыг бүрэн харуулдаггүй. Threshold туршилтууд checks (функциональ зөв байдал) ба thresholds (SLO) бие даасан гэдгийг баталсан — хариу зөв атлаа latency SLO-г хангаагүй байж болно. Өөрийн baseline (226.94 ms × 1.5 = 340 ms) дээр суурилсан SLO нь PASS/FAIL-ыг утга учиртай болгосон. Локал серверийн тест latency-г тусгаарлаж, оруулсан 100 ms саатал ба хэмжсэн p95 хоорондын нарийн (1:1) хамаарлыг баталсан. Ерөнхийдөө лаборатори throughput ба latency бие даасан хэмжүүр гэдгийг бодитоор харуулсан: throughput огцом өсөхөд latency тогтвортой байсан бол latency-г санаатай өөрчлөхөд throughput бараг хөдлөөгүй. Алдааны хувь (POFOD) 0% хэвээр байсан тул энэ орчинд хязгаарлагч хүчин зүйл болоогүй. Дүгнэж хэлбэл, гүйцэтгэлийн SLO нь зөвхөн бодит хэмжилтэд үндэслэсэн үед л утга учиртай бөгөөд ачааллын өөр хэмжүүрүүдийг (concurrency, latency) тусад нь туршиж байж системийн доройтлыг зөв тайлбарлах боломжтой.
